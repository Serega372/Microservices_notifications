# Microservices instances

Данный репозиторий содержит микросервисы, которые отвечают за обработку и отправку уведомлений и маршрутизацию в системе.
Начинать прочтение рекомендуется с репозитория `api-monitoring-auth`.

## Состав репозитория

В репозитории находятся следующие сервисы:

- **notifications-gateway**
- **email-service**
- **sms-service**
- **push-service**

Все сервисы могут масштабироваться как горизонтально так и вертикально.

## Архитектурная роль

### Notifications Gateway

`notifications-gateway` выполняет роль входной точки для отправки уведомлений, исключая traefik(см. репозиторий `api-monitoring-auth`).

Функции:
- принимает HTTP-запросы на отправку уведомлений;
- в зависимости от типа уведомления (`email`, `sms`, `push`) публикует сообщение в соответствующий Kafka-топик;
- реализует retry-механику при неудачной отправке сообщения в Kafka;
- сохраняет и обновляет состояние всех уведомлений в базу данных `notifications_db` (таблица `notifications_tbl`)
- сохраняет информацию о неотправленных сообщениях в базу данных `notifications_db` (таблица `retry_messages`).

### Email / SMS / Push сервисы

Сервисы:
- `email-service`
- `sms-service`
- `push-service`

Назначение:
- подписываются на соответствующие Kafka-топики;
- обрабатывают входящие сообщения;
- имитируют отправку уведомлений (логирование);
- случайным образом выбрасывают исключения для демонстрации обработки ошибок;
- обновляют состояние сообщений в базе данных `notifications_db`
- сохраняют информацию об обработанных сообщениях в базу данных `messages_db`:
    - `emails_tbl`
    - `sms_tbl`
    - `push_tbl`

## Взаимодействие сервисов

```text
client
   |
   v
traefik
   |
   v
notifications-gateway
   |
   v
kafka topics (email / sms / push)
   |
   v
email-service / sms-service / push-service
   |                        |
   v                        v
messages_db          notifications_db
```

## Отказоустойчивость

Для обеспечения отказоустойчивости система развёрнута следующим образом:

- 2 инстанса `notifications-gateway`
- 2 инстанса `email-service`
- 2 инстанса `sms-service`
- 2 инстанса `push-service`
- 2 брокера kafka в кластере

Каждый инстанс развёрнут на отдельной виртуальной машине.

## Retry-механизм

Если notifications-gateway не может отправить сообщение в Kafka:
- сообщение помечается как Retry;
- выполняется несколько попыток повторной отправки;
- при окончательной неудаче сообщение помечается как Error;

данные временно сохраняются в таблицу retry_messages базы notifications_db, после окончания retry попыток удаляются оттуда.

## Используемые технологии
- .NET
- Apache Kafka
- PostgreSQL
- Docker / Docker Compose
- Traefik

## Назначение репозитория

Данный репозиторий демонстрирует:
- работу микросервисной архитектуры;
- асинхронное взаимодействие через Kafka;
- отказоустойчивость сервисов;
- retry-логику при сбоях;
- разделение ответственности между сервисами.
